# SillyTavern 资产导入

外部资产（角色卡 / 世界书 / 预设）进入本项目的统一入口与既定边界。
页面在 `/sillytavern-import`。

## 产品口径：分流，不是映射

角色卡在格式上像「一个角色」，但作者常把世界设定、语气要求和写作约束写进
`description` / `scenario`。**照格式映射会把世界观埋进一个角色实体**——那样它
只在这个角色身上生效。

因此导入的主次是：

| | 定位 | 归宿 |
|---|---|---|
| World Book | 主线 | 既有知识库 + RAG |
| Preset | 主线 | 既有 `StyleProfile` + `StyleBinding` |
| Character Card | **素材来源** | 切段后分流到上面两条，角色事实才进角色 |

一个可佐证的事实：Character Card V2/V3 规范里 `data.character_book` 就是一本
**内嵌世界书**——卡片携带世界观是格式本身的设计，不是用户的用法偏差。

## 外部字段归一化（**最容易读错的地方**）

世界书条目的字段名有两套，取决于来源，**两套都必须认**：

| 独立导出的 World Info（最常见） | 角色卡内嵌 `character_book`（V2/V3） |
|---|---|
| `key` | `keys` |
| `keysecondary` | `secondary_keys` |
| `disable`（**反义**：true = 关闭） | `enabled`（true = 启用） |
| `order` | `insertion_order` |
| `comment`（兼作条目名） | `name` / `comment` |

`disable` 是反义的，这一处认不出的后果**不是少读一个字段**，而是把作者主动
关掉的条目当成启用导进检索，反过来影响写作。两种拼写同时出现时以
character_book 那套为准；不认识的原生字段一律 passthrough 保留。

条目容器也有两种形态：独立导出的 `entries` 是**以下标为键的对象**，角色卡内嵌
的是数组。两种都要吃。

## World Book 只做 Semantic Mode

条目进既有知识库、走既有 RAG 检索，**不实现 SillyTavern 的关键词注入引擎**。

理由是可维护性：两套检索机制并存会让「为什么这条没被检索到」永远说不清。
原文的 `key` / `keysecondary` 作为检索提示写进正文，让语义检索能命中它们。

导入按标题幂等：内容相同不产生新版本、不重新排队索引；内容变化是**同一份文档
的新版本**，而不是第二份文档。

## 写入边界

- **Preset 不接管模型路由。** 采样参数（`temperature` / `top_p` / …）原样留存
  供查看，但不写进模型设置、不改变实际调用参数。让一份导入的预设静默改写用户
  的模型配置，是最难察觉的一类破坏。
- **Preset 的指令留在 summary，不拆成结构化规则。** preset 不携带「这条属于
  叙事还是语言」的分类，硬拆会让 `StyleContract` 的 maturity 谎称 `structured`。
- **原文件里关闭的内容一律不生效**：禁用的世界书条目不进检索正文，禁用的预设
  指令片段不进写作规则。但它们要在预览/说明里可见，否则用户不知道被排除了什么。
- **导入不自动创建绑定。** 写法与知识库各自的绑定接口已经存在，其中知识库那个
  是**替换语义**（先清空目标的全部绑定再写入），拿它「追加一条」会静默删掉用户
  已有的绑定。绑定一律交给既有界面。
- **角色必须归属一本书**，世界设定与写法资产是全局的。有内容要进角色却没指定
  作品时，导入在写入前就拒绝，而不是写了一半才失败。
- **原文无损留存**：卡片/预设的原始 JSON 存进 `sourceContent`，解析器不认识的
  字段进 `rawImportedMetadata`。外部格式会继续演进，丢字段不可逆。

## 分流的判定边界

归属由**段落来自哪个字段**确定性决定，不经过模型：

| 字段 | 去向 | 是否需要人确认 |
|---|---|---|
| `system_prompt` / `post_history_instructions` | 文风 | 否，本来就是写作指令 |
| `first_mes` / `mes_example` | 文风 | 否，语气样本 |
| `personality` | 角色 | 否 |
| `character_book` | 世界设定 | 否，归属确定 |
| `description` / `scenario` | 按空行切段 | **是，不表态就拒绝导入** |

后两个字段是作者最常塞世界观的地方，也是导错代价最大的地方：世界设定进了角色
只对该角色生效，角色事实进了世界则对所有角色生效。**两个方向的错都不便宜，
所以交给作者判断而不是让模型猜。**

## 角色走提案，世界与文风直接入库

**导入不直接写正式角色库**——设计文档的硬要求。角色是小说范围的正式状态，
因此走既有 `ChangeProposal` 信封：导入产出一份 `pending_review` 提案
（逐项类型 `character_import`），用户在该作品的「变更提案」里审阅并执行后
才落成角色。

世界设定与写法资产**不走提案**：它们是全局资产，不属于任何一本书，塞进
绑 `novelId` 的信封语义不对。

这条分界的后果要对用户讲清楚：**一次导入会有两种结果**——世界设定与文风
立即可用（仍需绑定），角色则要再确认一次。

一处容易踩的既有规则：逐项的 `path` 终端段必须能在 payload 里找到同名键，
因为 apply 前会校验「展示的 `after` 等于实际写入值」。

## 按环节绑定写法（per-agent）

`StyleBindingTargetType` 的 `agent` 表示按**环节**绑定，`targetId` 存环节名。
已接线的环节：正文生成（`writer`）、规划（`planner`）、审校修正（`reviewer`）。
`STYLE_BINDING_AGENTS` 是那份清单，**加新环节要同时接进对应的解析调用**，
否则绑定建得出来却永远不生效——有一条扫源码的用例守着这件事。

服务端会校验按环节绑定时的 `targetId` 必须是清单里的值：放任意字符串通过，
拼错一个字母就是一条静默失效的配置，用户无从察觉。

优先级排在 novel 与 chapter 之间：环节比「整本书」具体，比「这一章」通用。
不做隐式层级覆盖，最终顺序由 `priority` 决定。

新增绑定目标时要同步的地方：双 Prisma schema 的枚举、**PostgreSQL 迁移**、
`styleEngine.ts` 的类型、运行时契约 `chapterRuntime/styleSchemas`、
优先级表（两处）、编译器标签表、路由校验、前端表单与标签表。

其中**迁移最容易漏**：SQLite 走 `prisma db push` 会自动跟上枚举变化，所以
只跑 SQLite 测试全绿并不代表 PostgreSQL 也认得——已部署的库执行
`migrate deploy` 后仍是旧枚举，第一次创建该类绑定就会被数据库拒绝。
漏掉运行时契约则会让合法绑定在组装上下文时被类型挡住。

## 未识别字段与原文留存

外部格式会继续演进，所以解析器不认识的字段一律保留，并且要走得出解析器：

- **预览显示**未识别字段（`unknownFields`），让用户知道有内容没被处理。
  这与 `ignoredFields` 不同：后者是我们认识但有意不导入的卡片元信息。
- **原文随导入结果留存**：写法资产存在 `StyleProfile.sourceContent`，
  角色存在提案载荷的 `sourceRaw` 里。批准之后仍然找得回来。
- 世界书目前只在预览里告知未识别字段，**不随知识文档留存原文**——
  知识文档没有存放原始文件的位置，写进正文会污染检索。这是已知边界。
